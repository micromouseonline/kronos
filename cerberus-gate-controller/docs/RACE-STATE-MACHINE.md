# Modified Gate Controller State Machine Specification for RATS

This document updates the original 3-gate state machine specification for the Registration And Timing System (RATS) to incorporate two architectural changes:
1. **Edge-Triggered Gates:** Sensor transitions are triggered by initial beam breaks (edge detection) rather than continuous beam obstruction (eliminating reliance on "cleared" signals).
2. **Course Timer Guard:** A boolean flag (`FirstRun`) ensures the course timer starts upon the robot's initial entry into the start cell and is **not** reset on subsequent run attempts during the same overall entry.

Inputs to the gate controller are described as events and can be generated by hardware beam breaks, button presses, or external radio messages.

## State Actions Table

| State | Name | Predecessors | Entry Condition | Actions | Exit Condition | Successors |
| :---: | :--- | :--- | :--- | :--- | :--- | :--- |
| **0** | **Calibrating** | Initial state | Power On | Displays/reports gate states | `NewMouse` message received | **9: NewEntry** |
| **9** | **NewEntry** | Any state | `NewMouse` received | Reset internal hardware timer.<br>Set `FirstRun = true`. | Immediate (Fall through) | **1: Waiting Robot** |
| **1** | **Waiting Robot** | 9, 5 | Transition from State 9 or 5 | Send `<TimerState, 1>` to RATS.<br>Wait for presence trigger. | Mouse Present in Start Cell (`ARM`) | **2: Robot at Start** |
| **2** | **Robot at Start** | 1, 4 | Presence in Start Cell | **If `FirstRun == true`:**<br>— Send `<CourseTimeMs, 0>` to RATS<br>— Set `FirstRun = false`<br><br>Send `<TimerState, 2>` to RATS.<br>Wait for start gate trigger. | Start gate triggered (`START`) | **3: Started** |
| **3** | **Started** | 2 | Start gate triggered | Send `<TimerState, 3>` to RATS.<br>Send `<C1SplitTime, 0>` to RATS. | Immediate (Edge mode) | **4: Running** |
| **4** | **Running** | 3 | Immediate from State 3 | Send `<TimerState, 4>` to RATS.<br>Wait for finish gate or start cell trigger. | Finish gate triggered (`GOAL`)<br><br>Start cell mouse present triggered (`ARM` / Abort) | **5: Finishing**<br><br>**2: Robot at Start** |
| **5** | **Finishing** | 4 | Finish gate triggered | Send `<TimerState, 5>` to RATS.<br>Send `<C1RunTime, value>` to RATS (3 times). | ARM event (presence gate or keypad `A`) -- **not automatic** | **2: Robot at Start** (or **1: Waiting Robot** if run limit reached) |

## Implementation Notes

State transitions always notify the host. Even though the host does not care, the information is logged there.

- **CALIBRATING (State 0)**
   Default state after power-on or reset. The controller can receive and deal with messages and gate requests. Gate events are reflected by the LEDs on each keypad key. This lets the user check the correct operation of the gates.
   - Timers all idle
   - Default Entry time set to 600 seconds
   - Default max run count set to 5
   - Time Display shows `.........`
   - Entry Time shows `00:00`
   - Run count shows `0/5`
   - Mouse Name, Run Times blank
   - Leaderboard unchanged (query: when should we reset/clear that?)
  **EXIT**:
   - Only a `NewMouse` event drops the controller out of `CALIBRATING` --
     either receiving the `<98,xxxx>` message, or a long press on the `A`
     key (same trigger State 9 itself responds to). `T` gets no response
     here.

- **NEW_MOUSE (State 9)**
   May be triggered _at any point_ by receipt of `<98,xxx>` or a long press on the `A` key
   - reset timers and run count
   **EXIT**
   - Automatic fall through to WAITING (state 1)

- **WAITING (State 1)**
   The controller  is now waiting for a robot to be placed in the start cell but may still respond to new message types 93, 94, 95 and 96 to set the conditions for the next run. This is deliberately broader than the PDF spec (`preferredMessageSequencesV2.pdf`), which ties 93-96 to State 9 only, immediately after `NewMouse`: host message order can't be guaranteed, so accepting these throughout WAITING is intentional, not a misreading -- don't "fix" this to match the PDF's stricter sequence.
   - timers idle
   - Mouse name displayed from last <98,xxxxx> message
   - Time Display shows `00:00.000`
   - Entry Time shows current maximum permitted time
   - Run count shows `0/5`
   - display will be updated if messages 93-96 are received
   **EXIT**
   - ARM event from presence gate or `A` keypad -> ARMED (state 2)
   - Also starts event time countdown

- **ARMED**
  Mouse now in start cell, ready to run. Note that UK rules may imply that removal is a lost run but we do not currently have a mechanism to cancel a run. The `T` key is available if we should decide to use it at some point.
  - On entry, the run timer set to zero and stops incrementing
  - Event timer is decrementing
  - Messages 93-96 are ignored
  - Message 92 can be used to 'undo' a run if a false start is triggered
  - `FirstRun`-guarded `<CourseTimeMs,0>` fires here (State 2, first start-cell arrival), not at State 9/`NewMouse` time as the PDF spec describes. This is intentional -- the PDF's placement (unconditional send immediately on `NewMouse`, before the robot has even reached the start cell) may itself be wrong or poorly worded; sending it on actual start-cell arrival is the more meaningful "course clock starts now" signal.
  **EXIT**
  - START event from gate or keypad `S` -> RUNNING (State 4, State 3 is skipped through)

- **RUNNING**
  Mouse is running in the maze but has has not yet reached the goal. There is no requirement that it does reach the goal from this state. It may crash or naturally return having done more exploration.
  - On entry, increment the run counter, start the run timer and notify the host with `<12,0>`
  - run timer increments continuously
  - event timer continues to decrement
  - can send periodic split times if desired to keep host in sync - not required. `<12,tttt>`
  - `T` key can be used to report a touch to the host. `<91,0>`
  **EXIT**
  - GOAL event from goal gate or `G` key -> GOAL state
  - ARM event from presence gate or `A` key -> ARMED

- **GOAL**
  Transitory state as mouse enters the goal
  - Stop the run timer 
  - Report the run time in milliseconds (three times to be sure) with `<13,mmmm>`
  - Record the run time as desired locally
  **EXIT**
  - Requires an explicit ARM event (presence gate or keypad `A`) -- **not**
    an automatic fall-through. ARM re-arms for the next run (State 2) if
    the run limit hasn't been reached, or drops back to WAITING (State 1)
    if it has. RESTART (`<98,xxxx>` or long-press `A`) starts a new mouse
    as usual. (This corrects an earlier draft of this doc, which described
    GOAL as auto-advancing to WAITING on a timer/debounce -- that was
    never actually implemented and has been confirmed as not wanted;
    manual ARM-to-continue is the real, intended behaviour.)

## State Diagram

```mermaid
stateDiagram-v2
    direction TB

    [*] --> State0: Power On
    State0: State 0 - Calibrating
    State9: State 9 - New Entry<br/>(FirstRun = true)
    
    State0 --> State9: NEW_MOUSE
    State9 --> State1: ALWAYS

    %% Composite state grouping operational states
    state Operational {
        direction TB
        State1: State 1 - Waiting For Robot
        State2: State 2 - ARMED / Robot at Start<br/>(If FirstRun == true:<br/> Send CourseTimeMs 0,<br/> FirstRun = false)
        State3: State 3 - Started<br/>(Entry: Send C1SplitTime 0)
        State4: State 4 - Running
        State5: State 5 - Finishing<br/>(Entry: Send C1RunTime x3)

        State1 --> State2: ARM
        State2 --> State3: START
        State3 --> State4: ALWAYS (Edge mode)
        
        State4 --> State2: ARM or ABORT
        State4 --> State5: GOAL

        State5 --> State2: ARM (run limit not reached)
        State5 --> State1: ARM (run limit reached)
    }

    %% Single transition representing global interrupt
    Operational --> State9: NEW_MOUSE <br/>(from any active state)
  ```
